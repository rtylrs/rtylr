and the ones that would mislead a new engineer are marked.

## Two gating mechanisms that are easy to confuse

| #   | Finding                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 14  | The brief, following the repo's own docs, treats `AppFlagGuard` and `APP_CONFIG` as the app-entitlement check. They are not the per-tenant licence: `resolveFlag` resolves a **launch** flag from PostHog then an env var then a hard-coded default (`packages/config/src/appGuards.tsx:44`), and `APP_CONFIG[app].allowedRoles` gates **roles** (`packages/config/src/apps.ts:34`). Per-tenant entitlement lives in hub (`packages/voxie/api/hub/app/v1/models.onk:8`), and the working precedent for reading it is CRM's add-on guard (`apps/crm/src/router.tsx:221`). Additionally `allFeaturesEnabled()` short-circuits every flag to true on self-host (`packages/config/src/appGuards.tsx:50`), so a degrade path conditioned on a false flag never runs there. Full treatment in `07-plumbing.md` |

## A retracted entry

Row 1 above previously reported that root `CLAUDE.md` was wrong to describe
`packages/voxie` as a nested submodule, and that the file was vendored as
ordinary blobs. **That was incorrect on every element, and the root file was
right.** Recorded here rather than deleted, because the row is cited by number
and because how it went wrong is the more useful finding.

What the original row got wrong:

1. **The conclusion.** `git ls-files -s voxie`, run inside `packages/`, reports
   `160000 0e48b902... 0 voxie`. The `.gitmodules` file in `packages/` declares
   it with its own upstream URL. It is a genuine nested submodule, exactly as
   root `CLAUDE.md` says.
2. **The method, which produced the conclusion.** The row verified with
   non-recursive `git submodule status`, which reports only top-level
   submodules by design and therefore prints `packages` alone. Adding
   `--recursive` prints `packages/voxie` too. Root `CLAUDE.md` itself instructs
   `git submodule update --init --recursive`, so the recursive form was the one
   to reach for.
3. **Its supporting citation.** It cited a `CLAUDE.md` inside `packages/` as
   already stating the correction. No such file is tracked in this repository or
   in the `packages` submodule. It exists in some working trees as an untracked
   local file, which is why the citation resolved for whoever wrote the row and
   for nobody else.
4. **Its line numbers.** It pointed at root `CLAUDE.md` lines 143 and 901. The
   submodule text is at `CLAUDE.md:119` and `:877`; line 143 is part of an ASCII
   directory tree, and line 901 does not exist in the committed file, which has 899. Those two numbers are written as prose here rather than as citations
   deliberately: written in citation form, a line that does not exist would fail
   the very check this entry is about.

Points 3 and 4 are the same defect from two directions: a citation checked
against a working tree rather than against what is committed.
`scripts/cross-app/verify-citations.mjs` now reports both, failing on a path
that is present but untracked and warning when a cited file is modified
locally, so this cannot recur silently.
